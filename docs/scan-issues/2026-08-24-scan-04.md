## Minor issues worth flagging (NOT blocking anything)

### 1. Check summary count ≠ findings list count

The check summaries claim more detections than the findings list shows:

| Check | Summary says | Findings shown | Delta |
|---|---|---|---|
| openai-anthropic | 6 detections | 4 findings | -2 |
| stripe-secret | 3 detections | 2 findings | -1 |
| supabase-service-role | 3 detections | 2 findings | -1 |
| aws-gcp-azure | 3 detections | 2 findings | -1 |
| github-gitlab | 3 detections | 2 findings | -1 |
| resend-sendgrid | 6 detections | 4 findings | -2 |
| hardcoded-jwt-secret | 2 detections | 2 findings | 0 ✓ |

**Root cause (likely):** the check iterates 3 sources — `fetchedScripts[N]`, `inlineScripts[N]`, and `pageHtml` (with script blocks blanked). The third source (pageHtml) is where our JSX `<code>{k.value}</code>` blocks render the fake keys into raw HTML text — so the pageHtml source matches too. But when the check emits a finding for it, the `normalizedKey` includes `sourceUrl` which is `null` for both inlineScripts AND pageHtml → both collapse to `"inline"` in the dedup key → the second insert is deduplicated at the storage layer → only 1 "inline" finding shown but the check's own counter recorded 2.

**Impact:** cosmetic. Findings are correct. Count in the summary just overstates by 1 per source with `sourceUrl=null`.

**Suggested fix:** either (a) use a distinct source-kind marker in `normalizedKey` (e.g. `inline_script` vs `page_html`) so they don't collide, or (b) make the summary count use post-dedup finding count.
