## Local regex verification — 2026-08-22

While the beta scanner was blocked, we did an independent check to prove the testbed content is correctly formatted for BugBuzzer's regex patterns. This isolates the failure to infrastructure — not to a logic bug in checks and not to a formatting bug in the testbed.

**Method:**
1. `curl` fetched the live HTML from `https://testbed.blockchainhq.xyz/`
2. Extracted all `<script src="…">` URLs (7 chunks, all under `/_next/static/immutable/chunks/`)
3. `curl` fetched each chunk → concatenated with the HTML → total ~587 KB → saved as `/tmp/all-content.txt`
4. Extracted BugBuzzer's exact regex from `packages/check-sdk/src/bundle-secret-extract.ts` into `/tmp/verify-fake-keys.mjs`
5. For the JWT-secret check (Row 5) which has more than one filter, also ran the assignment regex + name filter + Shannon entropy calculation locally

**Result: all 7 Batch 1 rows produced matches on the live deploy.** See batch-01 MD for the full row-by-row table.

**Fixes needed to reach this state** (all applied to testbed 2026-08-22, deployed to Vercel same day):

- GitHub `ghp_` value shortened to exactly 36 chars after prefix
- Supabase JWT payload changed from `iss=fake-testbed` → `iss=supabase`
- JWT secret moved from `FAKE_KEYS.jwt_secret` object (label had spaces → regex missed it) to `export const jwt_secret = "..."` + inline `<script>` with `var jwt_secret = "..."` assignments (64-char high-entropy random values)

**Conclusion:** The scanner infrastructure is now the single blocker for Batch 1. The testbed side is proven scanner-detectable through local regex simulation.
