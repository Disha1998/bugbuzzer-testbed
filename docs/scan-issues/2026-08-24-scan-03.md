## Root cause of the 6 misses

BugBuzzer has a `looksLikePlaceholder(value)` function at [`packages/check-sdk/src/bundle-secrets.ts:47-95`](../../../bugbuzzer/packages/check-sdk/src/bundle-secrets.ts#L47) applied to every candidate secret before it becomes a finding. If the (lowercased) value contains any of these words, the candidate is dropped:

```
"your", "example", "sample", "placeholder", "replace", "changeme", "change_me",
"change-me", "dummy", "test-key", "test_key", "test_secret", "secret_here",
"todo", "fixme", "insert", "fill_in", "fill-in", "put_your", "put-your",
"fake", "mock", "default", "my-api-key", "my_api_key", "enter_your",
"enter-your", "add_your", "add-your", "replace_me", "replace-me", "xxxx"
```

**This is correct, intentional design.** Real leaked production secrets are pure random strings. Any value containing "fake", "example", or "test-key" is almost always a schema example, a README code block, or a placeholder — flagging it would create false positives.

Every one of our 6 blocked fake keys contained the word "FakeTestbed" in the value. The one that fired (row 5) used pure random strings (`kQ7pNv3wR9bZmY6xL2fJhU4nT8aC1s…`) — no placeholder word, so it passed the filter.

**This is not a BugBuzzer bug. This is our testbed bug.** We were feeding the scanner values that look like placeholders because the strings say they're fake. To actually test the scanner, we need to feed it values that look like real leaked secrets — random garbage with no telltale English words.

Kept unchanged:
